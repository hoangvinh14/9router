## Success evidence

**Restart after a committed terminal.** In the isolated C0 fixture, the writer receives the native JSON response and checks the durable policy and one 105,900 nanoUSD terminal. It is then killed with SIGKILL before SQLite can close. A fresh Node process reads the same policy and terminal, returns 503 at the persisted limit, and adds zero POSTs and zero terminals. Raising the limit by one nanoUSD admits exactly one POST and one further terminal. Counted transport and HTTPS loopback suites both passed 14/14 on Node v24.21.0. Crash points before terminal acknowledgement, startup migration, and the wider platform matrix remain open.

**Crash points around SQLite commit.** The C0 fixture kills the writer before intent COMMIT, after intent acknowledgement and before transport, before the response read, after reading an incomplete response prefix, before terminal COMMIT, and after terminal COMMIT but before the application sees its acknowledgement. A fresh process sees zero intents and zero terminals before intent COMMIT. It sees one intent with no terminal after intent acknowledgement and before terminal COMMIT, including when the upstream has received the POST and the client has read part of the body. After terminal COMMIT it sees one intent and one terminal for 105,900 nanoUSD. It preserves the policy, permits a new request below the limit, and refuses at equality with no additional POST or terminal. Both compose suites passed 20/20 on Node v24.21.0, including HTTPS loopback.

**Calendar rollover.** The C0 fixture dispatches one millisecond before the Ho Chi Minh City month boundary and begins reading the response at the boundary. Its 105,900 nanoUSD debit uses the original dispatch month, week, key and price revision. At the month boundary the unchanged weekly limit still blocks with zero further POSTs. A new weekly window permits a fresh request, and the following weekly reset leaves that new month's exhausted limit in force. Both compose suites passed 21/21.

**Policy update and key rotation during settlement.** After the first POST and before the JSON body is read, a second SQLite connection saves a monthly limit of 105,900 nanoUSD and rotates the client key using the new policy version. The original response succeeds and stores exactly one 105,900 nanoUSD terminal linked to the original stable key, binding generation, price revision, week and month. The persisted policy advances to version 3 and generation 2. The revoked binding and the replacement at the exact monthly limit both return 503, adding zero POSTs and zero terminals. The cases exercise the candidate route and internal rotation primitive. On Linux Node v24.21.0, `node tests/fixtures/budget/run-composed.mjs` and the same command with `--tls` both passed 22/22.

**Standalone backup restore.** The Linux Node SQLite fixture takes the app's lightweight backup at 3,000,000 nanoUSD spent and then advances the source policy and spend to 6,000,000 nanoUSD. The fixture copies only the backup database file into a new path and opens that copy with a new adapter. Its policy, recorded spend and stored attempts match the snapshot. The next request at its restored limit is refused with zero transport invocations and zero new terminals. Foreign-key and integrity checks pass. The source keeps its newer policy and spend. The backup suite passed 15/15. This verifies the SQLite accounting boundary for a standalone snapshot. Credential rollback policy remains open.

**Credential state in older snapshots.** On disposable SQLite files, the snapshot taken before rotation resolves generation 1. The snapshot taken after rotation and before retirement resolves generation 2. Both snapshots predate the retirement event and retain the original attempt and terminal. The source refuses both credentials after retirement and retains the event. The backup suite passed 16/16 on Linux Node v24.21.0. This establishes the rollback consequence at the policy resolver. The operational restore policy must address credentials revoked after the snapshot before reopening ingress.

**Installed startup after restore.** The lightweight backup retains WAL mode and copies the empty log table and indexes. The installed driver opens the restored file with zero startup changes, skips late legacy input, reads the saved 105,900 nanoUSD and refuses the next invocation at the limit with zero new terminals. Backup checks passed 15/15 and schema classification 24/24 on pinned Linux Node v24.21.0.

**Previous lightweight backup format.** An offline fixture recreates the prior format with rollback-journal mode and no `requestDetails` schema. Installed startup refuses the unmodified snapshot. On a separate copy, switching to WAL and recreating the empty table and indexes from the current schema definition makes the installed driver accept it. Startup preserves the saved accounting rows, reads 105,900 nanoUSD and refuses the next invocation with zero transport calls or new terminals. The original snapshot is preserved. The startup suite passed 27/27. This evidence applies to the prior lightweight format with otherwise current schema and lineage. Broader donor migrations, credential rollback policy and cross-platform validation remain open.

**Preserved donor schema.** The old migration chain uses `apiKeyBindings`, `apiKeyAccounting`, `apiKeyAccountingAudit` and, from version 3, `apiKeyBudgetPolicies`. Startup and mutation inventory now treat these names as accounting markers before bootstrap or import. Startup rejects both donor-only and mixed schemas, leaving the stored spend and schema intact. Linux Node checks passed for startup (29/29), mutation barriers (13/13), request boundaries (12/12) and legacy import (85/85). Positive conversion of donor snapshots remains open. It requires a mapping for historical states, audit entries, identity and stored prices into the current schema.

**Donor conversion constraints.** The preserved binding identifies a key and fingerprint without per-attempt generations. Its ledger stores the original request and owner IDs, persisted price and usage, and explicit lifecycle state. Its audit also records waivers and manually corrected amounts. The current ledger validates terminal amounts by recomputing from stored normalized usage and price, and its admin event table models key retirement. An offline converter must preserve donor evidence and state, account for recorded corrected amounts exactly once, and avoid assigning a live generation or minting transport authority from historical rows. Using the existing settlement method for every donor row would lose distinctions and cannot represent a corrected amount without corresponding usage.

**Donor v2/v3/v4 regression.** Disposable databases reproduce the table shapes, indexes and append-only audit triggers from preserved revision `7a4f3a3e`. They contain pending, settled, unresolved, not-dispatched and waived rows, plus an unrecorded row in v4. Each includes a usage-based debit of 120,000 nanoUSD and an audited correction of 105,900 nanoUSD. Startup and the migration runner both refuse the old schema and preserve all rows and schema objects, including the exact total of 225,900 nanoUSD. The pinned Linux Node v24.21.0 startup suite passed 32/32. [Fixture](../../tests/unit/budget-startup-barrier.test.mjs).

**Offline source inspection.** On Linux Node 24, run `node scripts/inspect-legacy-accounting.mjs /absolute/path/to/backup.sqlite` on a standalone, quiescent donor backup. The command opens SQLite in immutable read-only mode and emits attempt counts by original state and the exact recorded total. It checks usage-based amounts against original prices, and manual corrections and waivers against the audit operation, version and amount. The v2/v3/v4 fixtures return 225,900 nanoUSD, keep the backup byte-for-byte identical, and reject an amount changed independently of its audit. The startup suite passed 32/32 on v24.21.0. Destination writing, activation and full migration qualification remain open. [Inspection command](../../scripts/inspect-legacy-accounting.mjs).
