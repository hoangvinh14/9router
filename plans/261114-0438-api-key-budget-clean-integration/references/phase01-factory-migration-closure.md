### Authority advancement asymmetry

P chat `prepareCredentialRefresh` captures acceptedRevision, checks initial unchanged, calls healthy(db), compares exact material/generation and requires !dirty before advance. `prepareAccountFailure` in **both chat and embeddings** checks allowed patch/material but after awaited update reads `read(db)` directly, no explicit dirty/health or acceptedRevision comparison.

Inspected caller chain: P `auth.markAccountUnavailable` builds bounded lock/error patch → session.accountFailure prepares → `await updateProviderConnection` → acknowledge. P connection repository `updateProviderConnection` uses **db.transaction**, not durableTransaction. SQL.js can therefore return a dirty in-memory update. This is a source-observed distinction, not evidence of an unsafe POST: final `assertPersistedSelection`, fresh digest and service gate remain downstream vetoes. Potential result is late refusal rather than silent bypass; don't drop those vetoes to fix compatibility.

Candidate correction before port: request-owned before/after revision token + same-lifetime healthy/clean own durable publication before adopting account-failure projection, exact permitted fields, refuse concurrent competing transition. No arbitrary “accept current config” after await. Need tests for dirty SQL.js update, competing prepare/ack, failed/unknown ACK, state drift, and actual successor intent+final POST0.
