# Database safety and accounting foundation

The database primitives have conditional Linux development acceptance; the accounting foundation adds internal ledger and recovery primitives. This is **not production activation or an all-platform/all-adapter durability certificate**. See the [prerequisite receipt](../plans/261018-0749-db-safety-pricing/reports/r7-conditional-linux-acceptance.md) and [accounting plan](../plans/261018-0214-accounting-foundation/plan.md) for evidence and open gates.

## Topology

One gateway writer process owns each canonical database-parent directory (normally `DATA_DIR/db`). Both the driver and direct adapter factories use the same exclusion namespace before opening SQLite/SQL.js. Multiple files in that directory are deliberately excluded together; separate databases require separate directories. Directory aliases resolve to the same namespace. Existing database symlinks, nonregular files and multiple hardlinks are refused.

Use a trusted local directory on a single host and PID namespace. This is not a cluster/network-filesystem lease or protection against hostile filesystem mutation by another user with write access. Ownership records and acquisition arbitration files must not be removed while any writer may be alive.

Acquisition writes a private instance record with restrictive permissions. Linux automatic stale recovery requires matching boot identity and provable dead PID; PID reuse, unverifiable liveness, malformed records or an interrupted arbitration directory remain blocked. There is no expiry/timeout unlock. Stop all relevant writers and verify identity/filesystem state before operator recovery. Do not copy an old clean ownership record over current state.

## API semantics

- Ordinary `run/exec/transaction` retain their existing synchronous application API. SQL.js ordinary writes are debounced, **not durable acknowledgements**.
- `durableTransaction(fn)` is synchronous and outermost. Successful native return requires verified WAL/FULL; SQL.js return follows export → same-directory temporary file → file fsync → rename → directory fsync. It also publishes preceding dirty SQL.js writes.
- Callbacks must be synchronous and must not schedule escaping work. Recognizable async functions are rejected before invocation. Returned thenables cause rollback and poison; JavaScript cannot cancel their continuation, so future adapter operations are denied.
- Use managed transaction methods only. Engine handles are private; raw BEGIN/END/COMMIT/ROLLBACK/SAVEPOINT/RELEASE are refused through SQL entry points. A lexical guard distinguishes trigger-body BEGIN/END from transaction control; trigger installation uses the write surface. `get/all` permit a single SELECT or allowed introspection PRAGMA, not mutation-returning statements or CTEs. The SQL API remains trusted application code, not a security sandbox for hostile modules.
- `health()` reports closed/poisoned/ownership state. `canMemoizePricing()` requires healthy ownership and no active managed transaction; SQL.js additionally requires no dirty image. Memo eligibility is not independent proof of power-loss safety.
- Publication or transaction-release/rollback uncertainty poisons future operations. A failed ACK is never converted into success because a later reopen sees the new value. SQL.js poisoned RAM is not exported on timer or close.
- Bun uses strict `close(true)` through its engine-close policy on normal close and initialization cleanup, so outstanding prepared statements are finalized before releasing ownership. Node/better retain their existing no-argument native close. Close failure does not release ownership; returned adapters become unavailable until a successful retry-close.
- The pre-open ownership token loses release authority after claiming; only the adapter's private lease may release following engine closure. Close removes background callbacks before releasing ownership; an engine-close or close-publication failure retains exclusion and denies subsequent reads/writes. A new process must use verified stale-owner recovery, not silently retry a second writable adapter.

## Selection, migration and backup

Engine unavailability is distinguished before application-file open. Unknown engine import errors, project module errors and application factory/open/initialization failures are fatal; they do not trigger fallback over uncertain state. The existing Node>=24 better-sqlite3 avoidance is preserved. No dependency or runtime installation is implied. Standalone builds retain the SQL.js runtime binary through [Next tracing configuration](../next.config.mjs); a successful compile alone does not verify fallback initialization.

The driver migrates and performs durable initialization before exposing an adapter. Declarative schema version 3 adds stable key bindings, attempts and append-only accounting audit; versioned migration 2 installs and verifies their constraints, indexes and audit triggers. Existing ACL and pricing data retain their meaning. A pre-schema backup is required before changing an existing database, including one with absent metadata. Backup failure stops migration.

Configuration imports also require a verified backup before mutation. [backup.js](../src/lib/db/backup.js) creates unique directories, verifies the database, includes existing accounting coverage material and retains the newest three backups. Native copies preserve table/index/trigger definitions and row counts; SQL.js first publishes preceding dirty state, then clones the acknowledged file and verifies integrity. Backups omit the reproducible `requestDetails` log. Failed SQL.js publication denies backup and poisons; backup never retroactively acknowledges an earlier failed operation. Destinations must be new files outside the live database directory. These are safety backups; managed physical restore and operator reconciliation remain separate work.

## Accounting identity and recovery

The initialized driver binds every key ID one-to-one to an HMAC fingerprint of its secret. The private HMAC material lives in `DATA_DIR/db/.accounting-coverage.json`, with restrictive permissions; the database retains its identity and key digest. Existing required missing, corrupt, insecure or mismatched material refuses opening before PRAGMAs/migration. A pristine interrupted sidecar initialization can resume using the same material. This assumes the trusted local directory described above; it does not detect an out-of-band rollback of both the database and sidecar.

Key creation/update/delete use durable transactions. An existing ID cannot change its secret, a secret cannot acquire another ID, and retired IDs/secrets cannot be reused. Retirement is persisted independently before delete commits; if the DB mutation fails, retirement still blocks reuse. Startup merges retained retirement into an older compatible database and disables stale restored keys. Lost retained bindings refuse authority instead of silently recreating them.

Database JSON export carries `accountingMetadata.kind = "configuration-only"` and non-secret coverage metadata. It is not a ledger or physical recovery bundle. Import preserves local attempts, audit, bindings, activation metadata and coverage material; it cannot reset them from JSON. Legacy exports without metadata or ACL remain supported, subject to identity checks; omitted ACL means unrestricted access. Identity collisions return HTTP 409 from the existing authenticated import route.

The independent sidecar also stores key/global coverage gaps, global maintenance, generations and bounded reconciliation receipts. Reconciliation requires an operation ID, actor, reason, evidence and expected generation. A durable DB audit precedes sidecar CAS acknowledgement; replay resumes a partial operation without duplicating audit. Key gap reconciliation cannot clear global maintenance. A failed sidecar publication makes that handle unavailable. Capacity exhaustion refuses further changes rather than pruning history. Management endpoints/UI and managed restore procedures remain unimplemented.

Before publishing a new exclusive driver lifetime, every prior pending attempt becomes unresolved with unknown outcome and null cost. Explicit close stops queued accounting work, durably resolves current pending attempts, closes the engine, then releases exclusion. Recovery failure retains exclusion. An unhealthy accounting adapter cannot export SQL.js RAM or release through this close path. Scoped SIGTERM controls cover these DB actions and another synchronous signal listener; they do not certify full server/network graceful shutdown.

See [the internal accounting interface](./ACCOUNTING.md) for P3 integration and exact evidence requirements. Installing schema never writes `ledgerStartedAt`; inference accounting, budgets and enforcement remain OFF.

## Limits / verification

Available evidence covers Node SQLite and actual SQL.js, plus bounded actual better-sqlite3 12.11.1 integration on Node22.23.2/Linuxx64 with a pinned ABI127 binding in a byte-identical private source mirror (R4:14 named scenario controls; see the prerequisite's `reports/better-r4-regression/receipt.json`). Actual Bun1.4.3/Linuxx64 now has a passing deterministic close-boundary test, three explicitly fault-injected lifecycle controls and14ordinary named scenario controls; see `reports/bun-r4-lifecycle/receipt.json` and `reports/bun-r4-ordinary/receipt.json`. This does not validate the repo's original installed ABI137 binding on Node22 or change Node>=24 avoidance. Windows/filesystem behavior and independent full-source review still need evidence; no all-platform acceptance is inferred from shared wrapper or adapter names. Combined R4 affected verification remains red at118pass/2usage-count failures across120assertions; those failures are not waived. If file/directory fsync cannot satisfy the required operation, the durable operation fails instead of returning weaker success. No support restriction or release claim is silently approved by this candidate.

Accounting controls run against actual Node SQLite and SQL.js on Linux. Bun/better/Windows accounting parity and full managed recovery remain release blockers owned by subsequent work; primitive test results above do not certify accounting parity. Process crashes do not certify power-loss behavior. Existing usage analytics retain their own semantics, including the two recorded baseline concurrency count failures; the separate ledger does not repair or reinterpret analytics history.
